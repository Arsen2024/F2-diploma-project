# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ТЕХНІЧНЕ ЗАВДАННЯ

## 1.1 Ідея проєкту

Проєктується та реалізується інтерактивна survival horror гра від першої особи, події якої відбуваються у системі підземних катакомб, що приховують забутий магічний підземний світ.

За сюжетом, близький друг головного героя зникає під час дослідження катакомб. Після припинення офіційних пошукових робіт герой самостійно вирушає на його пошуки. У підземеллі він знаходить залишене спорядження та останню записку з попередженням не продовжувати рух. Після цього внаслідок обвалу тунелю шлях назад стає недоступним, і герой змушений просуватися вглиб, де поступово виявляє існування прихованої магічної цивілізації та її мешканців — розумних істот з неоднозначною поведінкою, від ворожої до умовно дружньої.

Архітектура програмного рішення передбачає розділення основних ігрових підсистем (контролер гравця, AI істот, система збереження стану, система тригерів та скриптованих подій, UI/HUD) на незалежні, слабко зв'язані компоненти, що взаємодіють через визначені інтерфейси та систему подій Unreal Engine.

## 1.2 Інженерний опис аналогів
### Аналог 1: Alien: Isolation (Creative Assembly, власний движок)

- **Архітектурний патерн:** двошарова система AI — фоновий "Director AI" (відстежує глобальний стан гри, передає непрямі підказки) + дерево поведінки ксеноморфа (понад 100 вузлів, вирішує конкретні дії на основі сенсорних даних: зір, слух). Директор ніколи не повідомляє точну позицію гравця напряму.
- **Міжпідсистемна комунікація:** внутрішня подієва шина рушія між Director AI та деревом поведінки; задокументований debug-канал ручного керування AI-агентами через геймпад.
- **Персистентність стану:** класичної СУБД немає; ключова змінна "menace gauge" утримується в рантаймі на основі дистанції/чутності/видимості ворога, не зберігається між сесіями.
- **Критичні недоліки:** 100+ вузлів дерева поведінки створюють велике навантаження на етап контент-дизайну та QA (ручне балансування); система є детермінованим деревом рішень, а не справжнім машинним навчанням — ілюзія адаптивності досягається поетапним розблокуванням заздалегідь підготовлених гілок.

### Аналог 2: Amnesia: The Dark Descent / SOMA (Frictional Games, рушій HPL)

- **Архітектурний патерн:** власний рушій HPL (ядро на C++) + вся ігрова логіка на скриптовій мові AngelScript поверх нативного API — пряма паралель до моделі "C++ базові класи + Blueprints".
- **Міжпідсистемна комунікація:** фіксовані callback-функції рушія (OnEnter/OnStart/OnLeave), що викликаються на визначених подіях.
- **Персистентність стану:** власна система серіалізації з ручним маркуванням полів ([nosave]/[nodatasave]); звичайні змінні (int/float) НЕ зберігаються автоматично між сесіями.
- **Критичні недоліки:** задокументована розробниками проблема — стандартних рішень для серіалізації довільних скриптових об'єктів AngelScript не існувало, студія будувала власну serialize-систему з нуля; зміна структури скриптового класу ламає сумісність зі старими збереженнями, формального механізму міграції немає.

### Аналог 3: Resident Evil 2 Remake (Capcom, RE Engine)

- **Архітектурний патерн:** ядро на C++ + вся геймплейна логіка на C# поверх власної віртуальної машини REVM (ізоляція збоїв тайтлу від критичних падінь рушія); конвеєр ресурсів побудований навколо асетів з метаданими та розподіленим кешем конвертації.
- **Міжпідсистемна комунікація:** внутрішній конвеєр асетів з файловим хеш-моніторингом (FileSystemWatcher + MD5), а не рантайм-подієва шина.
- **Персистентність стану:** власний токен-орієнтований JSON-сумісний data engine (відкритий пізніше під назвою RE:Dox), оптимізований за використанням пам'яті.
- **Критичні недоліки:** архітектурний борг через вимогу повної зворотної сумісності з усіма попередніми тайтлами студії, що гальмує міграцію на нові версії мовної платформи (C#/.NET); на PC-портах неодноразово фіксувалися проблеми мікрозаїкань через компіляцію шейдерів.

## 1.3 Порівняльна інженерна матриця

| Критерій | **Мій проєкт** (UE5) | Alien: Isolation | Amnesia/SOMA (HPL Engine) | RE2 Remake (RE Engine) |
|---|---|---|---|---|
| Тип архітектури | Event-Driven + Component-Based, слабко зв'язані підсистеми через Blueprint Interfaces | Двошаровий AI: фоновий Director + foreground Behavior Tree | Рушій (ядро) + скриптовий шар поверх нього | Ядро C++ + геймплейна логіка на C# поверх власної VM (REVM) |
| Нативний/скриптовий шар | C++ + Blueprints | Не задокументовано публічно | C++ (ядро) + AngelScript (логіка) | C++ (ядро) + C# (логіка тайтлу) |
| Міжпідсистемна комунікація | Event Dispatchers/Delegates | Непрямі підказки Director → Behavior Tree | Фіксовані callback-функції рушія | Файловий хеш-моніторинг конвеєра асетів |
| Персистентність стану | Unreal SaveGame System з версіонуванням | Стан AI не персистентний | Власна serialize-система, ручне маркування полів | Власний JSON-орієнтований data engine (RE:Dox) |
| Відмовостійкість схеми даних | Версіонування save-структури закладено з початку проєктування | Не актуально | Задокументована вразливість, механізму міграції немає | Високий архітектурний борг через вимогу зворотної сумісності |
| Автотестування / CI-CD | Unreal Automation Testing Framework + GitHub Actions + UAT | Публічно не задокументовано | Публічно не задокументовано | Публічно не задокументовано |

## 1.4 Аналітичний висновок підрозділу

Проведений порівняльний аналіз трьох інженерно задокументованих систем-аналогів виявляє спільну закономірність: жодна з розглянутих архітектур не передбачає формалізованого механізму версіонування структури збережених даних як складової початкового проєктування. У рушії HPL ця проблема документально підтверджена як відома вразливість — зміна структури скриптового класу призводить до втрати сумісності зі старими збереженнями без штатного механізму міграції. У RE Engine аналогічна проблема проявляється на вищому архітектурному рівні: необхідність підтримувати повну зворотну сумісність з усіма попередніми тайтлами студії істотно обмежує швидкість еволюції платформи. Відсутність цього механізму як невід'ємної частини архітектури, а не post-hoc виправлення, є системною помилкою, якої дана кваліфікаційна робота свідомо уникає, закладаючи версіонування схеми стану на рівні початкового проєктування системи збереження.

Другою закономірністю є відсутність публічно задокументованого контуру автоматизованого тестування в усіх трьох проаналізованих системах. Натомість архітектурне рішення даного проєкту передбачає Unreal Automation Testing Framework та CI/CD-пайплайн на базі GitHub Actions і Unreal Automation Tool як обов'язкові компоненти, що забезпечує верифікацію коректності станових переходів штучного інтелекту та цілісності даних збереження на кожному етапі розробки.

Із запозичуваних рішень варто виокремити принцип слабкого зв'язування через непрямі сигнали, застосований у двошаровій архітектурі Alien: Isolation — цей принцип узгоджується з обраним патерном Event-Driven Architecture. Водночас буде свідомо уникнуто архітектурного компромісу, виявленого в RE Engine, де накопичення зобов'язань зі зворотної сумісності поступово ускладнює технологічну модернізацію: архітектура даної роботи проєктується з явним розділенням версій схеми даних з першої ітерації розробки.

## 1.5 Технічне завдання

### 1.5.1 Функціональні вимоги (Core Features)

1. **Контролер гравця** — рух від першої особи, взаємодія з об'єктами (line trace), керування станом персонажа.
2. **Штучний інтелект істот** — Behavior Trees, станові машини, AI Perception (зір/слух), динамічна зміна поведінкового стану.
3. **Система збереження та чекпоінтів** — серіалізація стану, авто- та ручні точки збереження, версіонування структури збережених даних.
4. **Система тригерів і скриптованих подій** — подієво-орієнтована комунікація між тригерами, AI та станом гравця.
5. **UI/HUD** — мінімалістичний інтерфейс стану персонажа та меню збереження/завантаження.
6. **Оптимізація** — профілювання (Unreal Insights), LOD для AI, оптимізація частоти опитування AI Perception.
7. **Контроль версій, CI/CD та організація проєкту** — Git/Perforce, GitHub Actions + UAT.
8. **Тестування та забезпечення якості** — Unreal Automation Testing Framework.
9. **Технічна реалізація суміжних ефектів** — освітлення (Lumen), VFX (Niagara), звук (MetaSounds), інтегровані через систему тригерів.

### 1.5.2 Технологічний стек

- **Мови програмування:** C++, Blueprints.
- **Архітектурні патерни:** Event-Driven Architecture, Component-Based Architecture, State Pattern / Behavior Tree Pattern, Interface Pattern.
- **Фреймворки та движок:** Unreal Engine 5 (AI Perception, Behavior Tree, Blackboard, Lumen, Niagara, MetaSounds, Enhanced Input System).
- **Зберігання даних:** Unreal SaveGame System (без класичної серверної СУБД — офлайн-гра).
- **DevOps-інструменти:** Git/Git LFS або Perforce, GitHub/GitLab, GitHub Actions + Unreal Automation Tool, Unreal Insights, Unreal Automation Testing Framework.
